# ADR-001: Verification Command Sequence and Positional Evidence Attribution

## Status
Accepted (Unreleased — Issue #363, PR #364)

## Context
During change preparation, `EngineeringPlanner` generates a pipeline of verification commands intended to execute in a specific order (for example, packaging or compiling before running tests, or sequential multi-step build tasks).

Prior to this decision:
1. `AgentChangeContract.fromPlan` transformed `plan.verificationCommands` into a sorted, deduplicated list via `.distinct().sorted()`.
2. Sorting mutated the execution sequence, causing `VerificationCommandExecutor` to execute commands in alphabetical rather than planned dependency order.
3. Positional evidence IDs (`verification-command-001`, `verification-command-002`, etc.) generated by `VerificationEvidenceIds.command(index)` referred to different commands between `EngineeringPlan` and `AgentChangeContract`, resulting in incorrect criterion evaluation (e.g., attributing a test failure to a package command or vice versa).
4. Deduplication destroyed repeated command invocations (e.g., `[A, B, A]`), preventing multi-phase pipelines requiring identical commands at different stages.

## Decision
1. **Ordered Sequence, Not a Set**: Treat `verificationCommands` as an ordered sequence throughout planning, contract creation, command execution, and criterion evaluation.
2. **Preserve Repetition**: Repeated commands (e.g., `[A, B, A]`) are preserved in exact sequence. Inserting, removing, or reordering repetitions alters the canonical representation and changes the contract fingerprint.
3. **Contract Schema Version 3.2**: Introduce contract schema version `3.2`. Under schema `3.2`, contract canonicalization serializes `verificationCommands` as a deterministic, unambiguous JSON array in exact list order without sorting or deduplication, avoiding newline collision between multiple commands and multiline single entries while preserving legacy newline-join semantics for schemas 2.0..3.1.
4. **Preserve Legacy Fingerprint Calculations (2.0..3.1)**: Historical schema versions (`2.0`, `2.1`, `3.0`, `3.1`) retain their historical `.distinct().sorted()` canonicalization when verifying contract fingerprints, ensuring existing stored contracts and verification receipts remain cryptographically verifiable.
5. **Fail-Closed Active Verification for Legacy Contracts**: Active verification (`EngineeringVerification.verify` and `vericore verify`) rejects legacy contract schema versions (`< 3.2`) with an actionable requirement directing the caller to re-run `prepare` to establish an order-preserved contract.
6. **Explicit Unsupported Version Rejection**: Unsupported schema versions (e.g., future or malformed versions not in `AgentChangeContract.SUPPORTED_SCHEMA_VERSIONS`) fail verification explicitly.
7. **Explicit Baseline-less Helper Behavior**: Contract creation without a repository baseline retains schema `2.0` (or `2.1` when agent context is present) for baseline-less test helpers, while production preparations require a repository baseline manifest and emit schema `3.2`.
8. **Positional Evidence IDs Maintained**: Retain 1-based positional evidence identifiers (`verification-command-NNN`) matching the exact, preserved command index. Do not introduce ad-hoc semantic command names or breaking schema changes to criterion bindings.

## Consequences
- Verification commands execute in the exact order generated by `EngineeringPlanner`.
- Positional evidence IDs (`verification-command-NNN`) are consistently bound to the same command across plan, contract, execution, and criterion evaluation.
- Active verification safely fails closed if presented with a legacy contract, preventing silent execution of out-of-order commands.
- Historical contracts can still be validated for fingerprint integrity.
