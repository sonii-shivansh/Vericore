## Release audit real-repository matrix

The 0.8.0 release audit executes both authoritative gates against:

- `spring-projects/spring-petclinic` at `main`
- `runelite/runelite` at `master`

The live repository gate includes deterministic evidence-graph checks, contract/plan binding checks, stale prepared HEAD detection, persisted MCP contract equality, source-mutation detection, final verification, MCP, REST, Gemini handling, and repository immutability.

Output-quality auditing separately captures and validates user-visible CLI/JSON/MCP/REST behavior and checks for stale `CodeContext` leakage.

Gemini is disabled in deterministic multi-repository live-gate calls; configured-provider checks may run separately, and quota/rate-limit handling is explicit rather than being treated as deterministic product failure.

## Consolidation decisions

### Live E2E vs Live Repository Gate

The older `live-e2e.yml` duplicated the authoritative real-repository path. Its functional and integrity coverage is now represented by `live-repository-gate.yml` and the complementary `live-output-quality.yml`, so the standalone workflow was removed.

### Agent Contract Integrity vs Live Repository Gate

The former standalone contract workflow's persisted-contract MCP equality, tamper, plan-mismatch, stale-prepared-HEAD, and final-verification scenarios are now executed inside `live-repository-gate.yml`, together with broader repository binding, evidence determinism, MCP, REST, and immutability coverage. The standalone workflow was therefore removed.

### Live Output Quality vs Live Repository Gate

These remain intentionally complementary: the release gate proves functional/integrity behavior, while output quality captures and parses actual command/REST/MCP output and checks for stale CodeContext leakage and malformed JSON.

## Documentation audit rules

1. Current release/version statements must describe `0.8.0` on the preparation branch.
2. Historical `0.7.0` release notes remain historical and must not be rewritten.
3. CodeContext references are classified before editing; migration/compatibility references remain when intentional.
4. Every documented CLI command must exist in the current CLI surface.
5. Architecture, semantic evidence graph, Engineering Reality, MCP, REST, roadmap and release documentation must describe the implementation actually present on the 0.8.0 preparation branch.
6. No documentation cleanup is deferred until after publishing `v0.8.0`.
7. The final machine-readable release-readiness report is required and must bind to the exact post-documentation candidate SHA and application version.
