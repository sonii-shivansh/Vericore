# Vericore 0.8.0 Release Readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn `release/0.8.0-preparation` into a fully audited release-candidate branch whose GitHub Actions prove the complete Vericore command surface, real-repository behavior, platform packaging, integrity/security contracts, and documentation/version consistency before the branch is merged and `v0.8.0` is published.

**Architecture:** Keep `release/0.8.0-preparation` as the release-candidate laboratory and make one authoritative reusable release-readiness gate the source of truth for end-to-end validation. Existing specialized workflows remain only where they provide unique platform/governance coverage; overlapping live-repository and contract tests are consolidated behind reusable jobs rather than duplicated. Documentation and release metadata are audited from the same candidate commit before release.

**Tech Stack:** Kotlin/JVM, Gradle, GitHub Actions, shell/PowerShell, JSON-based CLI artifacts, REST, MCP, real public Git repositories.

**Spec:** Approved 0.8.0 Release Candidate Validation System design.

## Global Constraints

- Work only on `release/0.8.0-preparation`; do not modify `main` and do not include PR #129.
- The release candidate must remain versioned as `0.8.0` throughout preparation.
- GitHub Actions is the execution environment for end-to-end validation; no laptop/local execution is assumed.
- Real-repository tests must prove the target repository is restored/unchanged after tests.
- Existing intentional CodeContext compatibility references must not be removed merely because they match a text search.
- Do not make release publication depend on Gemini availability; quota/outage behavior must be explicit and non-misleading.
- Do not delete a workflow until its unique coverage is mapped to another authoritative check.
- Every release-readiness claim must be backed by a completed GitHub Actions result or a documented, intentional skip condition.

## Review Focus

1. **Command success with incorrect output** — each command test must validate exit status plus output structure, identity/provenance, and key semantics.
2. **Cross-repository or stale evidence** — evidence, plans, contracts, and reality artifacts must reject wrong repository/commit state.
3. **Platform divergence** — Windows launcher/classpath and Linux/macOS distributions must execute the same release candidate successfully.
4. **Workflow false confidence** — overlapping workflows must not leave an important command untested or cause a green result to represent only compilation.
5. **Documentation/version drift** — every current-version claim must agree with `0.8.0`, while historical and intentional compatibility references remain accurate.
