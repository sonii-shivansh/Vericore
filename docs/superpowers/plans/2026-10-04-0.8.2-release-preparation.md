# Vericore 0.8.2 Release Preparation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prepare Vericore `0.8.2` from the post-`0.8.1` remediation state, prove the release is internally consistent and certified, and leave `main` untouched until the release branch is fully ready.

**Architecture:** Keep the existing Vericore architecture unchanged. This release is a patch release centered on version synchronization, release-state documentation, explicit documentation of the corrected machine-readable contracts, regression/release verification, and certification; no unrelated refactoring or feature work is permitted.

**Tech Stack:** Kotlin/JVM 21, Gradle Kotlin DSL, Kotlin serialization, Kotest/JUnit 5, GitHub Actions, four platform distributions, SHA-256 release checksums.

**Spec:** Approved in-chat 0.8.2 release-preparation design.

## Global Constraints

- `main` must not be modified directly during preparation.
- The working branch is `release/0.8.2`, created from the current `main`.
- Release version must be exactly `0.8.2` everywhere that represents the current application/build release.
- Historical `0.8.1` references must remain where they document the already-published release or its audit history.
- No unrelated product features, dependency upgrades, or architectural refactors are part of this release.
- The organization-analysis response change and architecture-artifact schema change must be documented accurately rather than silently rewritten.
- The release must pass the repository's existing release-audit, CI, packaging, live-repository, and regression gates before merge.
- The final release tag must point at the exact certified commit that is merged to `main`.

## Review Focus

- Current-release version drift: every executable/build-facing version source must resolve to `0.8.2`.
- Historical-release contamination: `0.8.1` audit/release history must not be accidentally rewritten as `0.8.2`.
- Machine-readable contract drift: organization hotspots and architecture artifact schema changes must be covered by tests/documentation and remain deterministic.
- Release artifact consistency: archive names, embedded version, checksums, and platform outputs must all identify `0.8.2`.
- Certification integrity: all required GitHub Actions/release gates must pass on the exact commit intended for `v0.8.2`.
